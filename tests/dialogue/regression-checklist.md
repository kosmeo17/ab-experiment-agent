# AB 实验 Agent 回归清单

## 覆盖剧本

- A：普通运营完整链路，从必要性到待补齐骨架。
- B：直接问样本量 / 灰度，但实验必要性缺失。
- C：推送系统灰度实验，区分方案设计和配置准备。
- D：飞书初稿评审、修订和文档更新边界。
- F：韩国超级曝光价格实验实测复盘，验证标准库映射、对象/场景边界、主流程回归和飞书交付。

## 必须通过

1. 必要性先于指标、分组、样本量和灰度。
2. `有点下滑`、`感觉变差`、`提醒比较弱` 不能直接放行；先问来源、幅度/口径或策略和问题的关系。
3. 用户问 `跑几天`、`灰度多少`、`10% 够不够` 时，如果必要性缺失，先问必要性，不计算样本量。
4. 核心指标先单选；过程指标按实际决策需要选择；实验指标中只保留唯一护栏。
5. 实验对象和触发场景必须分开问。
6. 对象、触发场景和指标清楚后，先问数据支持 / 新增数据需求，再问分组。
7. 分组清楚后先问互斥关系，再进入样本量 / 灰度；不要在样本量测算前强制要求 owner 提供互斥比例。
8. 用户不知道流量、基线、历史波动或灰度时，只有对话已经进入样本量 / 灰度阶段，才路由 `$da-agents`。
9. `发 vs 不发` 是有效推送分组；不发组是对照组，不是配置缺失。
10. 推送系统配置走 `$cms`；不要问 ABTest 服务开关或开关值。
11. `Campaign`、`Message`、`is_plan_to_send` 只在配置准备阶段出现，不在早期方案设计阶段出现。
12. 飞书文档是方案来源，不是数据验证；文档里的数据说法只能写 `文档已提供`，不能写 `已查数`。
13. 必要性、指标、对象、触发场景、数据支持、分组、互斥、样本量 / 灰度缺任一硬门槛时，不生成正式飞书文档。
14. 文档修改先在聊天中确认建议；最终一次合并更新，保留原文并追加 `建议更新内容：`。
15. `$cms` 默认先只读校验；任何写入、发布、启用、停用或影响生产的操作必须单独确认。
16. PRD 里的 `只做中英`、示例语言、截图语言、端上支持范围或配置项范围不能自动变成实验人群限制；有歧义先问这是实现范围还是人群范围。
17. 使用代理事件、近似分母或历史替代口径查流量/基线/样本量时，正式文档顶部状态必须写 `基于代理口径估算/待正式事件复核`，不能写成完全验证。
18. 正式飞书文档不要出现 `业务域与 AI 推断` 这类内部标题；用 `业务判断与风险说明` 或并入 `背景与必要性`。
19. 核心指标必须由 owner 确认；AI 推荐指标未确认前，不进入正式样本量计算。
20. 观察指标不能重复核心指标；同口径拆解只能作为过程诊断指标。
21. 分组方案必须通过 `陌生读者无疑问` 自检；默认商品、SKU、价格公式、促销/非促销、币种/四舍五入、A/B 是否相同或唯一变量不清楚时，阻塞样本量、灰度和正式文档。
22. 互斥问题必须问具体线上冲突：同一批用户、同一入口、价格/SKU、活动折扣、展示文案或核心指标；不要只问“是否需要互斥”。
23. 数据查询前必须展示拟用事件/字段、筛选条件、分子分母、统计单位和时间窗口，并提醒埋点管理系统或数据 BP 复核；用户确认后再走 `$da-agents`。
24. 样本量默认按公司 notebook 口径组织：首周 WAU、新 WAU 次周衰减、过去 14 天核心指标初始值、MDE、指标类型、最小实验组样本比例；ARPU/均值类不得用付费率样本量替代。
25. 样本量计算前必须先检查可访问的公司 notebook / 公司计算器 / 数据 BP 结果 / 用户提供文件；如果存在 `/Users/sequioa/Downloads/计算实验的预估样本量.ipynb` 或其他可访问公司计算器，必须先读取或运行，不能先用本地公式。
26. 样本量结果必须声明来源：公司 notebook / 公司计算器 / 数据 BP / 本地粗估脚本 / 手工公式 / 待确认；未实际读取用户提供的计算器或文件时不能声称已按其底层逻辑计算。
27. 本地脚本、手工公式、历史近似或 AI 推断只能标记为粗估 / sanity check；不能输出正式样本量、正式灰度、正式周期可行性、`已验证`、`已定稿` 或 `可进入配置准备`。
28. 有效最小实验组比例必须说明是否已扣灰度/互斥；若 WAU 未扣限制，灰度 20% × 最小实验组 30% = 6%；若 WAU 已扣限制，不能重复乘。
29. DA 结果默认先翻译业务含义，不展示 SQL、CSV、本地路径、日志 ID 或指标入库选项。
30. 方案/飞书文档完成后，应提醒可继续整理实验配置上线清单，并提醒配置前确认双端测试通过；实验跑完后可用 `$da-agents` 辅助复盘。
31. 真实数据查询必须走三步：确认已知信息、说明 agent 拟查数据、展示查询口径并让 owner 确认；不要把任务推给用户自己查。
32. 样本量阶段不要一次性问一堆输入；默认只问一个最高优先级问题，或让 owner 确认一份查询口径后由 agent 查数。
33. MDE 面向 owner 必须解释为“希望识别多小的提升”，并给 5% / 10% / 15% / 20% 选项和推荐值；不要让用户填 0.1。
34. ARPU / 收入类指标的分子和分母必须来自同一批实验场景用户；全站 VIP 收入不能除以实验场景用户数并写成正式口径。
35. 正式灰度按 `计划周期内符合条件用户 × 互斥后可用比例 × 灰度比例 × 分组比例` 覆盖每组所需样本判断；商业化收入/转化类默认先按约 14 天稳定周期，而不是用 100% 灰度追求最短填样本。
36. 风险观察灰度和正式实验灰度必须分开；10%-20% 短期看异常不能替代正式实验周期。
37. 存在互斥关系但 owner 未提供互斥比例时，样本量阶段应先反推 `所需有效流量 = 灰度比例 × 互斥后可用比例`，并给出组合建议；不得把互斥比例缺失作为测算前 P0 阻塞。
38. 最终周期可行性、最终灰度、正式配置或正式飞书文档前，必须确认最终采用的灰度比例和互斥配置组合，并计算每组实际样本。
39. 用户点名查某个 table、字段、事件定义、埋点名、口径是否支持或单个数据时，必须先完成这个窄查询并停下；不得在返回结果前自动进入样本量、灰度、正式文档、CMS 配置或其他 AB 阶段。
40. 点名查询结果必须包含业务解释和 1 个下一步建议：说明查到什么、口径/限制、对当前 Gate 或判断的影响；不要因为限制范围而只返回生硬字段或数字。
41. 用户说样本量、灰度、查数或计算结果 `有问题 / 不对 / 重新算 / 复核一下`，但未说明怀疑对象时，必须先用 1 个同维度问题确认复核层级：公式、历史输入、灰度/互斥、核心指标/MDE，或点名查询；确认前不得默认重算、重查、跑样本量、查其他来源或扩大到完整 AB 流程。
42. 主流程已经明确下一步时，不要为了执行 `Grilling 式澄清闸门` 而额外提问；该闸门只在用户内容听不懂、指代不明、怀疑对象不清或执行路径不清时触发。
43. 核心指标和护栏指标必须映射 AB 系统标准库，保留标准名称和 key；找不到时写`需新增标准指标`，不得把国家、VIP、历史行为或实验组拼进指标名自造名词。
44. 收入、付费、价格、SKU、折扣、Paywall 类核心指标的唯一护栏是留存率；留存、活跃、互动、召回类核心指标的唯一护栏是收入 ARPU。投诉、退款、负反馈、支付失败等只写风险说明或上线监控。
45. 实验对象只定义随机分组资格，实验场景只定义符合对象的用户实际受影响的行为或位置；场景不得重复对象条件，也不得补造入口、页面、弹窗、点击或事件。
46. 每个实质性回复必须说明已确认项、当前阶段和唯一下一步。局部追问或点名查询结束后，必须回到最早未完成 Gate；用户说`继续`时只能推进该 Gate。
47. 所有 Gate 通过后，下一步必须询问`是否创建飞书文档？`。用户同意但无目标空间写权限时，请求最小必要授权；不得默认生成本地 Markdown 或 XML。
48. owner 在沟通中提供的支撑性原始证据必须完整保留在最终方案文末`来源与附件`；正文的`背景必要性`等位置仍需说明关键证据支持什么，二者不能互相替代。
49. 正式方案章节统一使用`具体分组说明`，表头统一使用`用户实际看到的内容`。内容默认应让读者理解并复核关键差异；简述不足时，必须补充关键细节、示例或来源链接/附件。

## 禁止回退

- 不要因为 owner 看起来有经验，就跳过完整 AB 流程。
- 不要把配置字段提前当成实验方案字段。
- 不要把用户给出的灰度比例当成已验证计算结果。
- 不要把低成本证据动作当成自动批准实验的结果。
- 不要用精美文档格式掩盖方案硬门槛缺失。
- 不要把实现范围误读成实验对象范围。
- 不要把代理口径误写成正式验证结论。
- 不要把内部推断标签直接放进对外正式文档标题。
- 不要把 AI 推荐核心指标当成 owner 已确认。
- 不要用普通转化率样本量替代 ARPU/均值类样本量。
- 不要在 owner 刚写方案时追实验 ID、配置路径或看板 ID。
- 不要把 DA 内部产物发给运营，除非用户明确要求。
- 不要说 `拿这份给数据/DA 查` 或让 owner 误解成需要自己查数，除非数据能力确实不可用且已说明边界。
- 不要把 MDE 当行业黑话直接抛给 owner，也不要让 owner 填小数。
- 不要把 7 天流量足够当成必须 100% 灰度快速结束实验；优先保证稳定周期并反推灰度。
- 不要在样本量阶段追问“互斥比例是多少”；先告诉 owner 需要多少有效流量，再让 owner 按互斥池资源和用户暴露风险选择组合。
- 不要把“查一个 table / 字段 / 事件 / 数据”扩展成完整 AB 流程、样本量灰度测算、正式文档修改、CMS 检查或 skill 规则调整。
- 不要把“样本量有问题 / 重新算 / 复核一下”默认理解成公式重算；先确认用户怀疑的是公式、输入、灰度/互斥、核心指标/MDE，还是只要点名查数。
- 不要把 Grilling 式澄清执行成凡事先问；能从当前 AB 阶段明确推出下一步时，应继续推进。
- 不要把标准库未映射的临时描述包装成正式实验指标、key 或固定观察窗口。
- 不要把对象条件复制到实验场景，也不要由历史数据或业务常识补造产品入口。
- 不要在局部问题回答完后丢失主流程，或省略唯一下一步。
- 不要在方案通过后跳过飞书创建确认，或在授权失败时用本地 Markdown 替代飞书交付。

## 回归执行方式

每次修改 `$ab-experiment-agent` 规则、追问库、输出结构或飞书工作流后，至少按 A-D 和 F 五个剧本做一次反向检查。发现新失败模式时，要同步更新三处：底层规则、对应剧本、这份回归清单。
