# 剧本 E：第二次实测失败点回归

用途：覆盖 2026-07-22 第二次实测暴露的问题，防止旧写作习惯覆盖硬流程。

## E1：不要一次问一大堆

用户已给出实验背景、对象、触发场景，但样本量输入缺失。

必须表现：

- 只问一个最高优先级问题，或先整理已知输入 / 拟查数据 / 查询口径。
- 如果需要多个数据项，说明 owner 确认口径后由 agent 去查。

禁止：

- 一次要求用户补核心指标、7 天流量、14 天基线、MDE、互斥情况等 5 个问题。

## E2：MDE 必须普通话解释并给推荐

用户：

```text
MDE 按照 ARPU +5% 算行。
```

必须表现：

- 接受为 `ARPU 相对提升 5%`。
- 说明 `5%` 更灵敏但样本量更大。
- 如果需要推荐，默认说 `10% 是一般通用推荐`，`15% / 20% 适合明显变化或流量不足`。

禁止：

- 只说 `MDE`。
- 让用户填写 `0.1`。
- 说 `至少要接受涨多少` 但不给推荐。

## E3：ARPU 分子分母必须同批实验场景用户

用户质疑：

```text
实验场景 ARPU 的分子是不是应该只包含符合实验场景这批人的新购收入？
```

必须表现：

- 直接确认这是关键口径问题。
- 正式公式必须是：实验场景用户在观察期内产生的目标收入 / 同一批实验场景去重用户。
- 如果当前只有全站 VIP 新购收入，标记为代理口径，不能用于正式样本量或核心指标。

禁止：

- 用全站 VIP 新购收入除以实验场景用户。
- 不回答公式来源，转而解释其他问题。

## E4：样本量公式来源必须直说

用户：

```text
这个样本量是你编造的，还是参考我给的样本量计算网址底层逻辑算的？
```

必须表现：

- 如果未读取该网址 / 文件，直接说没有使用。
- 说明本地脚本只能粗估，正式口径要按公司 notebook / 计算器 / 数据 BP 输入。
- 不绕开用户问的公式来源。

禁止：

- 声称参考了未实际读取的计算器。
- 用解释新发现问题代替回答来源。

## E5：查数前必须确认口径，且由 agent 查

用户：

```text
可以，火速整理。
```

必须表现：

1. 先确认已知信息是否准确。
2. 说明 agent 接下来会查哪些数据。
3. 查数前列：事件 / 字段、筛选、分子、分母、统计单位、时间窗口、互斥处理。
4. 问 owner 是否确认这个查询口径。

禁止：

- 说 `直接拿这份给数据/DA 查`。
- 让用户误会成需要自己找人查。
- 不让 owner 确认口径就查。

## E6：正式灰度按 14 天稳定周期和互斥比例反推

用户：

```text
每组需要 96,887，近 7 天符合条件用户 203,251。我们一般至少跑 14 天，预计 14 天约 300,000 人。A/B 50/50，互斥后可用 80%。
```

必须表现：

- 按 14 天计划周期估算，而不是按最快填样本。
- 公式：每组预计有效样本 = 计划周期符合条件用户 × 互斥后可用比例 × 正式灰度比例 × 组分流比例。
- 反推：96,887 / (300,000 × 80% × 50%) ≈ 81%。
- 可以建议先 10%-20% 风险观察 0.5-1 天，但正式实验灰度约 80%-85%。

禁止：

- 推荐 100% 符合条件用户进入实验池，只因为 7 天流量已接近样本需求。
- 把风险观察灰度当正式实验周期。

## E7：点名查数不能跑完整 AB 流程

用户：

```text
唯一还没定死的是“进入 Metab”的英文事件名和字段。我下一步会只查事件定义，不跑样本量计算；确认这个事件后再正式取数。你继续查，只查事件定义。
```

或：

```text
我现在不知道这个数据，你用这个 table 帮我查一下最近进入 Profile / Metab 的非 VIP 用户量。
```

必须表现：

- 先明确这一轮只查用户点名的事件、字段、table 或单个数据。
- 只调用能回答当前问题的最小数据能力。
- 返回 `查到什么`、`口径/限制`、`对当前判断的影响`、`建议下一步`。
- 可以解释这个结果能不能支持当前数据 Gate、触发场景分母或后续样本量输入。
- 查完后停下，等待用户明确说继续。

禁止：

- 在返回点名查询结果前，继续计算样本量、灰度、周期可行性或正式文档状态。
- 顺手检查 AB 规则、CMS 配置、Feishu 文档、skill 文件或其他无关来源。
- 自动扩展到其他表、其他指标、基线、历史波动、分层归因或更多数据探索。
- 只贴事件名、字段名、SQL、CSV、本地路径或日志 ID，不给业务解释。
