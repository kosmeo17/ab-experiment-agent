# 数据判断

用本参考判断 AB 实验方案是否有足够的数据支持。本文件只是判断框架；不要编造数据，也不要把飞书 / Lark 文档访问当成真实数据验证。需要真实数据时，由主流程按边界路由给 `$da-agents`；路由前必须让 owner 确认已知信息和拟查口径。

## 数据能力边界

允许：

- 询问当前有哪些证据、基线、事件、标签、看板或指标支持。
- 说明数据判断标准。
- 把数据支持标记为 `已确认`、`待确认` 或 `需要新增数据需求`。
- 在当前阶段已经准备好查数时，整理已知信息、拟查数据和查询口径，owner 确认后路由 `$da-agents`。
- 当当前环境不能直接查数时，明确说明能力不可用，再给出可交接给数据 BP / DA 的口径；不要默认让 owner 自己去查。
- 只有当用户已经提供完整输入，且已经确认没有可访问的公司 notebook、公司计算器、数据 BP 结果或用户提供的样本量文件时，才使用本地 `scripts/sample_size.py` 做初步样本量计算。该结果只能标记为粗估 / sanity check。

禁止：

- 在用户没有贴出结果时声称已经查过数据。
- 像已经验证过一样生成 SQL。
- 在 owner 未确认拟用字段、事件、筛选、分子分母、统计单位和窗口前，调用 DA、TA、Doris 或其他数据平台工具。
- 对 owner 说 `你拿这份给数据 / DA 查`、`你让数据同学查一下`、`你把数据补齐再来`，除非当前环境确实没有可用数据能力且已经说明能力边界。
- 把飞书 / Lark 文档访问当成数据验证。
- 把平台不可用当成方案已经准备好的证明。
- 让用户在本 skill 里调试外部数据连接。
- 存在可访问的公司 notebook、公司计算器、数据 BP 结果或用户提供的样本量文件时，绕过该来源，直接用本地公式、`scripts/sample_size.py`、AI 推断或历史近似输出正式样本量或灰度判断。

## 真实数据查询硬流程

涉及数据支持、事件可用性、样本量输入、灰度、监控或复盘真实读数时，必须按以下顺序走；这是硬流程，不是写作建议：

1. 先给 owner 确认已知信息是否准确：实验目标、核心指标、实验对象、触发场景、分组、互斥或灰度限制。
2. owner 确认后，说明 agent 接下来会查哪些数据，以及这些数据分别解决什么判断。
3. 查数前先列查询口径：事件 / 字段、用户筛选、分子、分母、统计单位、时间窗口、是否排除互斥或非实验场景用户。让 owner 确认口径后，再路由 `$da-agents`。

不要把第 2 步写成让用户去查；表达应是 `我会继续按这个口径查...`、`你确认口径后我去查...`。

## 点名查询模式

当用户说 `用这个 table 查 X`、`查一下这个字段`、`只查事件定义`、`确认这个埋点名`、`看这个 table 是否支持` 或类似表达时，进入点名查询模式。这类请求的目标是先把一个不确定数据点查清楚，不是自动继续推进完整 AB 流程。

执行规则：

1. 先复述当前只查的问题，避免把查询目标扩大。
2. 只查询能回答该问题的最小来源；不得在结果返回前追加其他指标、其他表或下游样本量 / 灰度查询。
3. 如果当前查询需要口径确认，只问这个查询所需的最小口径；不要顺手追问完整 AB 方案字段。
4. 查完后停止，等待用户明确继续。

返回格式：

```text
查到什么：...
口径/限制：...
对当前判断的影响：...
建议下一步：...
```

`对当前判断的影响` 必须把数据翻译成业务含义，例如说明这个事件能不能作为触发场景分母、这个字段能不能支持实验对象圈选、这个 table 是否足以进入样本量输入。不要只贴字段名或数字。

`建议下一步` 只能给 1 个动作；可以建议继续查分母、确认埋点 owner、回到样本量输入或先补数据需求，但不能直接执行，除非用户明确说继续。

## 证据质量

方案至少包含以下一种具体证据时，实验必要性更强：

- 当前数据：基线率、漏斗流失、流量规模、收入 / 用户行为分布、历史趋势。
- 历史实验或发布结果：过去相关策略曾影响或未能影响相关指标。
- 产品观察：特定场景中可重复的用户行为或运营现象。
- 风险或成本证据：直接上线可能伤害用户、收入、留存、安全或运营负担。

如果没有完整证据但现象具体，先问场景和行为。如果证据和现象都模糊，暂停 AB 路径，先问受影响的用户行为。

## 指标可行性

批准指标前，检查四个问题：

1. 核心指标能否被这次策略直接影响。
2. 核心指标能否在计划实验周期内观察。
3. 分母或分析单元是否清楚。
4. 可能副作用是否有护栏指标。

核心指标和观察指标不能混在一起：

- 核心指标：用于判断实验方向和解释结果的主要指标。
- 观察指标：用于解释漏斗变化和副作用。
- 护栏指标：即使核心指标提升，也可能阻止上线。

收入实验中，除非 owner 明确提供其他业务标准，否则优先使用实验周期内 ARPU 或实验用户人均净收入作为主判断标准。新 SKU 的单项购买率通常只是诊断指标，除非它已经覆盖总增量价值。

核心指标必须由 owner 确认。AI 可以推荐核心指标，但在用户确认前，只能写 `推荐核心指标` 或 `待确认核心指标`，不得基于该指标继续做正式样本量计算。

核心指标和观察指标要去重。观察指标用于解释漏斗变化、副作用或护栏影响，不能重复核心指标本身。若需要拆解核心指标，标记为过程诊断指标，例如点击率、点击后付费、购买人数、ARPPU 或收入拆分。

## 曝光和触发可行性

触发场景必须说明用户什么时候真正看到或受到策略影响。触发场景模糊时，不批准分组、曝光定义或样本量判断。

在引导和逐步方案生成中，询问当前系统、看板或推送系统是否已经支持已确认的类别：

- 实验场景。
- 实验人群。
- 核心指标。
- 观察指标。
- 护栏指标。

默认问题不要列具体推送或事件字段，例如分组分配、触发事件、送达、点击或聊天窗口跳转。这些细节只在 owner 要求实现交接，或方案进入配置上线辅助后才有用。如果任一已确认类别不支持或未知，标记为新增数据需求或配置支持缺口。

## 样本量输入

不要先问灰度比例，也不要一上来就执行 DA。进入样本量阶段后，先向 owner 展示已知输入和拟查输入。

已知输入通常包括：

- 用户已确认的核心指标及指标类型。
- 实验对象和触发场景。
- 分组比例，以及由此得到的最小实验组分流比例。
- 已知灰度、互斥或实验池限制。
- MDE 建议值或 owner 已给出的最小可接受提升。

拟查输入通常包括：

- 实验场景首周 WAU。
- 过去 14 天核心指标初始值。
- 新 WAU 次周衰减系数；如果可根据目标用户/场景稳定推断，要暴露假设。
- ARPU/均值类所需的过去 14 天对照组和实验组转化率或转化人数占比。
- 流量稳定性；默认至少看过去 15 天或 30 天，按业务周期选择。

发起真实查询前，必须先列出：

- 事件 / 字段。
- 用户筛选条件。
- 分子和分母。
- 统计单位，例如用户、曝光或订单。
- 时间窗口。

同时提醒 owner：如果不确定这些字段是否正确，可以先在埋点管理系统复核或让数据 BP 帮忙确认事件定义；owner 确认口径后再路由 `$da-agents`。

然后判断核心指标类型：

- 转化率 / 比例。
- 均值 / 用户级人均值。
- ARPU / 收入。
- 次数 / 频次。
- 比率。

只有核心指标、指标类型、有效最小实验组比例和拟查口径清楚后，才问或查询基线、最小有意义提升、计划周期，以及必要时的方差 / 标准差或公司 notebook/计算器输入。

如果输入缺失，说明缺什么以及为什么重要。不要批准周期或灰度。

## 数据需求输出

使用运营能看懂的表达：

```text
新增数据需求：待确认。当前方案还没说明触发场景是否能被系统识别，也没说明核心指标的分母和统计单位。没有这两项，后续曝光、样本量和复盘口径都会不稳定。
```

如果用户已经贴出足够证据：

```text
新增数据需求：暂未发现必须新增项。已知用户范围、触发场景、核心指标和护栏方向都能被描述清楚；后续真实读数会按已确认口径查询，实际事件 / 看板是否覆盖仍需在查询或配置交接时复核。
```

## DA 结果表达

DA 返回后，先翻译成业务判断，再补技术口径。不要把 SQL、CSV、本地路径、日志 ID、指标入库选项或内部中间文件默认展示给运营；只有用户明确要求复现、看 SQL、下载文件或沉淀指标时才展示。

推荐：

```text
过去 30 天这个入口流量整体稳定，可以作为样本量估算的流量基础；但核心指标初始值仍需按正式实验分母复核。
```

避免：

```text
已生成 CSV：...；SQL：...；日志 ID：...
```
