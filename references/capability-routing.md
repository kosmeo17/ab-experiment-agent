# 能力路由

当 AB 实验需要产品规则、数据验证、CMS 配置、飞书文档、配置上线辅助或复盘支持时，使用本参考。

## 原则

本 skill 不是固定流水线。它负责 AB 实验判断和方案设计；当某个状态需要外部能力时，再把明确问题交给对应 skill。

不要强制每个实验都依次经过 `$frank-prd-writer`、`$da-agents`、`$cms`、飞书、配置和复盘。只调用当前阻塞问题真正需要的最小能力。

对用户介绍能力时，必须分开讲两件事：

- 本 skill 自己能做什么。
- 它可以联动哪些外部能力。

不要把联动能力说成本 skill 已经自动完成或能持续代替 owner 监控。

## 点名查数 / 查字段边界

当用户明确要求 `用这个 table 查一下...`、`只查事件定义`、`查字段名`、`看这个口径支不支持`、`查一下这个数据` 时，先把它当作一个独立的小任务，而不是恢复完整 AB 流程。

调用外部能力前，必须先用一句运营能看懂的话写清楚当前未解决问题，例如：`这一步只确认“进入 Metab”的正式事件名和可用字段，不计算样本量。`

允许：

- 只调用能回答当前问题的最小能力。
- 判断查到的字段、事件或数据是否能支持当前 Gate。
- 给 1 个最相关的下一步建议，例如继续确认分母、补一个事件、或回到样本量输入。

禁止：

- 在返回当前问题答案前，自动扩展到其他 table、其他指标、样本量、灰度、正式文档、CMS 配置或 skill 修改。
- 因为查数时看到了 AB 背景，就重新跑必要性、分组、互斥、样本量等完整流程。
- 把“建议下一步”当成已经获得用户授权的继续执行。

停止条件：

- 已找到用户点名要查的结果。
- 已确认当前来源不能回答该问题，并说明缺哪个字段、事件或权限。
- 发现关键歧义必须由 owner、埋点系统或数据 BP 确认；此时只问这个歧义，不继续探索。

## 本 skill 能做什么

- 判断实验必要性，区分应该 AB、直接上线、直接修复或先做低成本验证。
- 评审已有实验方案，按 `问题 / 影响 / 建议` 输出阻塞点。
- 根据一个点子引导设计新的实验方案。
- 根据 PRD、飞书或已知产品规则生成运营侧 AB 方案。
- 设计或校验核心指标、观察指标、护栏指标、实验对象、触发场景、分组、互斥和样本量输入。
- 组织样本量计算口径，给出粗估或交给公司 notebook / 数据 BP 的正式输入。
- 生成或整理飞书 AB 实验文档。
- 文档完成后，协助整理实验配置上线清单；实际配置、发布和双端测试通过仍由负责人确认。
- 实验结束后，辅助复盘结果、解释指标变化、判断是否继续、停止、扩大或调整。

## 可联动能力

- `$da-agents`：查基线、流量、字段/事件可用性、样本量输入和实验复盘数据。调用前必须先让 owner 确认拟用字段、筛选、分子分母、统计单位和窗口。
- `$cms`：在配置清单确认后，协助只读校验、dry-run 或配置交接。任何生产写入、发布、启用、停用或回滚都必须按 CMS skill 单独确认。
- 飞书 / Lark：读取、整理、生成或更新文档；文档读写不等于数据系统验证。
- `$frank-prd-writer`：产品规则、触发链路、前后端逻辑或 PRD 来源不清时使用。

不要写 `实验过程监控提醒` 这类未确认自动化能力。需要表达上线前支持时，用 `配置上线辅助：整理/校验待确认清单，实际发布、双端自测通过和最终上线由负责人确认`。

## 外部能力版本提醒

`$cms`、`$da-agents`、飞书 / Lark、UI / PRD 等外部能力可能独立更新。AB skill 不应假设自己打包时携带或本机当前安装的外部能力就是最新版本。

当任务要读取最新 CMS 配置、用户标签、指标库、事件定义、生产结构、真实数据或复盘结果时，先读取 `references/dependency-version-checks.md`，并用一句话提醒 owner：

```text
这一步依赖本地 $cms / $da-agents 的最新能力。要不要先检查是否有新版本，再继续只读查询？
```

如果 owner 选择继续按当前版本查，可以执行只读查询，但输出要保留边界：`按当前本地版本读取`。不得在 owner 未确认的情况下自动更新外部 agent、CLI 或项目仓库。

## 实验状态

| 状态 | 含义 | 需要时调用的能力 |
| --- | --- | --- |
| `idea_or_reviewing` | 想法、粗略方案或已有方案正在澄清 / 评审 | 只有当产品规则、触发行为、前后端逻辑或 PRD 来源不清时，才调用 `$frank-prd-writer` |
| `ready_to_plan_doc` | 运营侧 AB 方案可以形成正式文档 | 飞书可作为文档读写渠道；如果基线、流量、事件支持或样本量证据已经是阻塞点，可调用 `$da-agents` |
| `data_feasibility_needed` | 设计已清楚到可以定义数据问题，但数据可行性或证据未知 | 调用 `$da-agents` 查基线、流量、事件 / 指标可用性、样本量输入、监控或读数 |
| `ready_for_launch_review` | 方案可以进入上线前评审，但配置未必完整 | 整理待确认清单：承载系统、安全风险、追踪 / 看板计划、自测范围、回滚 owner / 动作和未决上线阻塞；实际测试通过和上线由负责人确认 |
| `ready_to_config` | 方案已有足够承载系统细节，可以交接配置 | 调用 `$cms` 做只读发现、dry-run 和已明确确认的写操作；ABTest 系统和推送系统都适用 |
| `ready_to_launch` | 配置、自测、追踪 / 数据回传和回滚确认已经由负责人完成 | `$cms` 只处理已确认的启用、发布或回滚动作；需要监控或读数时调用 `$da-agents` |
| `experiment_readout` | 实验正在监控、解读或复盘 | `$da-agents` 提供结果数据，本 skill 负责解释、判断质量和下一步动作 |

## 能力边界

- `$frank-prd-writer`：产品规则能力。用于产品行为、触发链路、UI / 后端规则或 PRD 来源不清时；轻量运营实验不强制使用。
- `$da-agents`：数据能力。实验前 / 配置前用于基线、流量、事件支持、指标可用性、样本量输入；实验结束后用于读数和复盘。它不是只能在最后一步使用。不要承诺持续自动监控，除非当前环境已有明确可用的自动化能力。
- `$cms`：配置能力。用于 ABTest 系统和推送系统的配置发现、dry-run 和安全操作。必须先只读；任何写入、发布、启用、停用、回滚、删除或刷新缓存都需要按 CMS skill 单独确认。
- 飞书 / Lark：文档渠道。读取或写入文档不等于验证数据系统状态。

## 用户标签发现

当实验对象、推送目标人群、用户圈选、互斥、进入限制或配置准备涉及用户标签时，先读取 `references/user-labels.md`，再路由给 `$cms` 做只读发现。

默认判断：

- 用户标签来源是 CMS-CLI 的推送系统 / 标签管理，不是 AB skill 本地知识库。
- 重点看标签名称、备注、状态和层级；一般优先使用三级标签。
- `label_id` / id 是配置标识，不是面向运营的主名称。
- 标签存在不等于流量、基线或样本量已验证；真实规模和效果仍按 DA 流程确认。

不要只因项目目录、飞书索引或本地文档没有标签资料，就回答“没有用户标签库”。如果 CMS 只读发现失败，说明失败原因和当前影响，并停在 `标签来源待确认`。

## 承载系统确认时机

不要只因为实现方式未知就阻塞普通运营方案草稿。如果实现方式已知，保留在内部 / 配置交接里。如果未知，普通面向运营的草稿不要展示 `承载系统`、`实现方式` 或 `待产品/研发/数据讨论确认`。

只有当实现方式会改变实验对象、分组逻辑、触发定义或指标归因时，才在起草方案前追问实现方式。

具体配置语言属于 `ready_to_config`，不是早期方案草稿：

- ABTest 系统配置：服务开关、开关值、指标树 / 结果回传、实验配置、必要时的 seed / SRM / AABB 风险。
- 推送系统配置：Campaign、Message、目标人群、灰度比例、AB 分组比例、`is_plan_to_send`、内容差异、活动类型、触发条件、进入限制、转化事件、归因窗口、送达 / 点击 / 转化追踪，以及回滚 / 暂停动作。

## 推送系统实验类型

所有推送系统变体仍然是 AB 实验，只是配置对象和实验变量不同：

- 推送系统-灰度实验：验证发 vs 不发。使用推送系统灰度逻辑和 `is_plan_to_send` 区分计划发送与不发送用户。
- 推送系统-AB 实验：验证不同推送内容或配置。当前已知约束是 AB 组共享节点、延迟、用户条件、推送类型和节点结构；除非 CMS 新证据说明不同，否则主要变量是内容配置。
- 推送系统-灰度 & AB：灰度控制计划发送池，AB 分组控制计划发送池内的内容或配置差异。

推送系统实验不要问 ABTest 服务开关或开关值。配置检查可以路由给 `$cms`，但必须使用推送系统字段语言，而不是 ABTest 开关语言。

## 文档完成后的提醒

当方案或飞书文档完成后，简短提醒 owner 后续还能继续做两件事：

- 如果方案确认无误，可以继续帮忙整理实验配置上线清单，并提醒用户再次确认实验配置中双端测试是否已经通过。
- 实验跑完后，可以用 `$da-agents` 辅助复盘。

只做提醒义务，不需要知道实验是否已经结束。
