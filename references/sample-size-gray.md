# 样本量与灰度

判断样本量、实验周期或灰度时，使用本参考。

## 原则

灰度是计算结果，不是凭直觉选择的百分比。先看触发场景流量，再判断核心指标类型，最后收集该指标类型所需输入。

当指标类型或方差信息缺失时，不要承诺精确样本量结果。此时下一步是要求补充缺失数据、使用公司样本量计算器，或请数据 owner 确认。

分开两个问题：

- 实验必要性：相比直接上线、不做或低成本验证，AB 是否仍然是合适方法。
- 结果可判定性：这个 AB 是否有足够样本检测预期核心指标提升。

小流量会削弱结果可判定性，但不自动取消实验必要性。如果 owner 有有效的风险控制理由，例如担心 Push 策略伤害 D1 留存或用户体验，AB 可以继续，但方案必须把样本量输入、预期提升 / MDE 和结论可靠性标为 `待确认`。

区分实验流量池比例和组间分流比例。`100% 符合条件用户进入实验流量池，再 50/50 分组` 可以是有效设计。不要只因为样本小就建议更小流量的安全验证。如果瓶颈是真实触发场景流量，降低实验流量池会让结论更弱；优先考虑延长周期、扩大对象 / 场景、接受更大的可检测效果阈值，或限制结论解释。

当转化率 / 比例指标或均值 / 用户级人均值指标的输入完整时，可使用 `scripts/sample_size.py` 做初步计算。把结果写入方案或评审时必须带上限制说明。不要直接用该脚本处理比率指标，除非数据 owner 已经把比率转换为有效的用户级转化或均值指标。

## 默认统计设置

除非来源方案或公司计算器另有说明，使用以下默认值：

- 显著性水平：alpha = 0.05。
- 统计功效：0.80。
- 检验方向：默认双侧。
- 分析单元：默认用户级，除非方案明确了其他稳定单元。
- 实验周期：通常至少 2 周，除非场景流量极高或有已验证的短周期理由。

如果多个实验组都和同一个对照组比较，标记需要多重比较处理或数据 owner 确认。不要把三组及以上实验静默套用单一 A/B 的样本量逻辑。

## 第 1 步：先问流量

根据 owner 能提供什么，问以下任一项：

- 计划实验人群规模。
- 触发场景 WAU。
- 日曝光。
- 日触发用户。

用流量判断方案在拟定周期和灰度上限内，是否可能收集足够用户。如果流量明显太小，先停下，不问灰度百分比；回到必要性处理：如果 AB 是风险控制所需，可以继续但标记可判定性风险；如果必要性较弱，推荐一个非灰度的下一步。

不要规定固定历史窗口。如果需要时间窗口，请 owner 或数据 owner 选择能代表业务周期、上线时机和用户行为频率的窗口。

面向运营的表达：

```text
下一步先看样本量是否支撑 AB。请先补一个数：符合这次实验意向的人群或触发场景，大概有多少可实验用户/曝光/触发量？
```

## 第 2 步：判断核心指标类型

样本量判断前，先给已确认的核心指标分类：

| 指标类型 | 示例 | 默认处理 |
| --- | --- | --- |
| 转化率 / 比例 | 点击率、购买转化率、入口率、完成率 | 使用两比例样本量逻辑 |
| 均值 / 用户级人均值 | 人均发消息数、人均活跃天数、人均时长 | 使用两样本均值逻辑；需要标准差或方差 |
| ARPU / 收入 | ARPU、人均收入、曝光用户人均支付金额 | 按均值 / 用户级人均值处理，但标记长尾风险，并要求历史方差或计算器结果 |
| 次数 / 频次 | 发送次数、访问次数、查看资料次数 | 默认按均值 / 用户级人均值处理，除非数据 owner 指定计数模型 |
| 比率 | 收入 / 曝光、点击 / 展示、用户可产生多个分母的成功 / 尝试 | 要求分子、分母、聚合单元和计算器 / 数据 owner 确认；不要朴素当作简单转化率 |

如果指标类型不清楚，问：

```text
这个核心指标的分子、分母和统计单位分别是什么？比如按用户算、按曝光算，还是按订单算？
```

## 第 3 步：按指标类型收集输入

转化率 / 比例指标需要：

- 基线转化率。
- 最小可检测效果，或业务可接受的预期提升，可为绝对值或相对值。
- 组数。
- 组间比例。
- 计划周期。
- 如果不使用默认值，补 alpha 和 power。

脚本示例：

```bash
python3 scripts/sample_size.py --metric conversion --baseline 0.08 --relative-mde 0.1 --groups 2 --daily-traffic 50000 --duration-days 14
```

均值、ARPU、收入、次数或频次指标需要：

- 基线均值。
- 最小可检测效果，或业务可接受的预期提升，可为绝对值或相对值。
- 使用相同分析单元的历史标准差或方差。
- 组数。
- 组间比例。
- 计划周期。
- 是否存在离群值，以及该指标通常如何稳定处理。

ARPU / 收入指标的观察窗口要和计划实验周期对齐。如果周期未知，先写 `实验周期内 ARPU/人均净收入`，并在问基线方差前收集计划周期。引导输出中不要默认使用 7 日或 14 日 ARPU。

当指标已有稳定用户级标准差时，可用脚本示例：

```bash
python3 scripts/sample_size.py --metric mean --baseline 3.5 --relative-mde 0.05 --stddev 8.2 --groups 2 --daily-traffic 50000 --duration-days 14
```

比率指标需要：

- 分子定义。
- 分母定义。
- 聚合单元。
- 基线比率。
- 最小可检测效果。
- 历史方差、计算器结果或数据 owner 确认。
- 组数、组间比例和计划周期。

## 第 4 步：判断灰度

当每组所需样本量已知或已由数据 owner 提供后：

- 总所需样本 = 各组所需样本量之和；如果组间比例不等，需要按比例调整。
- 可获得样本 = 计划周期内触发场景流量 × 符合灰度和互斥条件的流量。
- 灰度比例应足以覆盖所需样本，同时满足风险和互斥约束。

如果总所需样本大于可获得样本，推荐一个下一步：

- 扩大实验对象或触发场景。
- 延长周期。
- 接受更大的可检测效果阈值。
- 减少实验组。
- 如果 AB 无法产出可靠结论，改用低成本验证路径。

如果瓶颈是真实场景流量，不要建议单纯提高灰度。
当 owner 已经说样本小且风险理由需要 AB 时，不要建议降低实验流量池作为“安全验证”。这时应说明实验可以继续做风险控制，但核心指标提升结论可能样本不足。

## 输出建议

面向运营时避免公式化解释。说明缺什么和下一步是什么：

```text
现在还不能判断灰度比例，因为核心指标是 ARPU，不是普通转化率。请先补这个指标在代表性历史窗口下的用户级标准差，或者贴一下样本量计算器输出；拿到后才能判断当前流量和周期是否够。
```

评审报告中说明指标类型和样本量证据是否充分：

```text
样本量与灰度：待补充。核心指标属于转化率类，但方案只给了灰度 10%，没有给场景流量、基线转化率和最小可接受提升，因此无法判断 10% 是否足够跑出结论。
```
