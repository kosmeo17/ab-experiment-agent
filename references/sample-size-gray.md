# 样本量与灰度

判断样本量、实验周期或灰度时，使用本参考。

## 原则

灰度是计算结果，不是凭直觉选择的百分比。先确认核心指标已经由 owner 选定，再按公司样本量 notebook 口径整理已知输入、拟查数据和假设；owner 确认后再查数或计算。

如果存在互斥实验，必须先让 owner 确认互斥实验占用的同入口/同人群流量比例，或本实验互斥后剩余可用比例。不要按 AI 假设比例继续，不要默认 100% 可用，也不要用历史比例替代 owner 确认。

当指标类型或方差信息缺失时，不要承诺精确样本量结果。此时下一步是先说明 agent 会按什么口径查缺失输入，或说明需要公司样本量计算器 / 数据 BP 提供哪类正式输入；不要默认让 owner 自己补标准差、贴计算器输出或拿清单去找 DA。

分开两个问题：

- 实验必要性：相比直接上线、不做或低成本验证，AB 是否仍然是合适方法。
- 结果可判定性：这个 AB 是否有足够样本检测预期核心指标提升。

小流量会削弱结果可判定性，但不自动取消实验必要性。如果 owner 有有效的风险控制理由，例如担心 Push 策略伤害 D1 留存或用户体验，AB 可以继续，但方案必须把样本量输入、预期提升 / MDE 和结论可靠性标为 `待确认`。

区分实验流量池比例和组间分流比例。`100% 符合条件用户进入实验流量池，再 50/50 分组` 可以是有效设计。不要只因为样本小就建议更小流量的安全验证。如果瓶颈是真实触发场景流量，降低实验流量池会让结论更弱；优先考虑延长周期、扩大对象 / 场景、接受更大的可检测效果阈值，或限制结论解释。

正式样本量优先使用公司 notebook、公司计算器或数据 BP 结果。`scripts/sample_size.py` 只能做粗估/初筛；把结果写入方案或评审时必须带上限制说明。不要直接用该脚本处理比率指标，除非数据 owner 已经把比率转换为有效的用户级转化或均值指标。ARPU / 收入类不得用普通付费转化率样本量替代。

## 提升幅度 / MDE 表达

面向 owner 默认不要直接问 `MDE 用多少`。如果必须提 MDE，第一次出现要解释成：`希望这次实验能识别多小的提升，提升越小，需要的样本量越大`。

收入、价格、SKU、Paywall 类实验，优先给相对提升选项并给推荐：

- `5%`：更灵敏，适合希望捕捉小幅收入变化的高流量场景，但需要更多样本。
- `10%`：一般通用推荐，适合多数商业化实验先估算。
- `15% / 20%`：适合预期效果较大、流量不够或只需要判断明显变化的实验，样本量压力更小，但只能识别更大的变化。

不要让 owner 填 `0.1`、`0.05` 这类小数；如果内部计算需要，自己转换为 10% 或 5%。推荐任何 MDE 数字时，都必须说明业务依据，例如：是否属于高流量场景、是否希望捕捉小幅收入变化、是否只是初步估算、样本压力是否可接受。不能只说 `建议 5%` 或 `建议 10%`。

## ARPU / 收入同批用户口径

ARPU、实验用户人均净收入、VIP 新购收入等收入类核心指标，分子和分母必须来自同一批实验场景用户：

- 分子：实验观察期内，进入实验场景且符合实验对象的用户产生的目标收入。
- 分母：同一观察期内，进入实验场景并参与实验分组的去重用户。
- 分析单元：默认用户级。

禁止把 `全站 VIP 新购收入` 除以 `实验场景去重用户`，也禁止把 `进入实验场景用户收入` 除以 `全站活跃用户`。如果当前数据只能拿到全站收入、全站 VIP 收入或非同批用户收入，只能标记为 `代理口径 / 待正式口径验证`，不能作为正式核心指标或正式样本量输入。

## 默认统计设置

除非来源方案或公司计算器另有说明，使用以下默认值：

- 显著性水平：alpha = 0.05。
- 统计功效：0.80。
- 检验方向：默认双侧。
- 分析单元：默认用户级，除非方案明确了其他稳定单元。
- 实验周期：通常至少 2 周，除非场景流量极高或有已验证的短周期理由。

如果多个实验组都和同一个对照组比较，标记需要多重比较处理或数据 owner 确认。不要把三组及以上实验静默套用单一 A/B 的样本量逻辑。

## 公司 notebook 口径

样本量阶段按以下输入组织，而不是只按 `日流量 × 实验天数` 粗算：

- 实验场景首周 WAU。
- 新 WAU 次周衰减系数：根据目标用户和触发场景推断；无法稳定判断时标记假设，不知道时可按 1 做保守占位。
- 核心指标初始值：默认查过去 14 天。
- 希望识别的提升幅度：面向 owner 用 5% / 10% / 15% / 20% 表达，并给推荐；内部可映射为 MDE。
- 指标类型：比值类 / 均值类 / ARPU，由已确认核心指标判断。
- 最小实验组样本比例：来自流量分组、灰度和互斥后的有效样本比例。
- ARPU / 均值类额外输入：过去 14 天对照口径和实验口径转化率或转化人数占比，并按 notebook / 模拟逻辑判断。

## 第 1 步：确认核心指标和已知输入

样本量不能基于 AI 单方面推荐的核心指标计算。先确认：

- 核心指标是否已经由 owner 确认。
- 指标类型是什么。
- 实验对象和触发场景是否已经清楚。
- 分组比例和最小实验组分流比例是什么。
- 是否有灰度、互斥、实验池限制。
- 希望识别的提升幅度是否已有 owner 标准；没有时给 5% / 10% / 15% / 20% 参考，并明确推荐值。
- 若存在互斥实验，互斥占用比例或互斥后剩余可用比例是否已由 owner 确认。

面向运营的表达：

```text
先确认样本量计算口径。当前我会按你确认的核心指标「X」计算，它属于「Y」类指标；分组是 A/B = 50/50，所以最小实验组分流比例是 50%。如果这个核心指标不是你最终想用的指标，要先改掉，再算样本量。
```

## 第 2 步：列出拟查数据和字段

真实取数前，先列出拟用口径并让 owner 确认：

- 拟查数据：首周 WAU、过去 14 天核心指标初始值、新 WAU 次周衰减系数、必要时 ARPU/均值类转化率。
- 事件 / 字段：必须写到具体事件名和字段名，不能只写 `VIP 净收入`、`成功曝光用户`、`去重曝光用户数` 这类业务描述。
- 用户筛选条件。
- 分子和分母。
- 统计单位，例如用户、曝光或订单。
- 时间窗口。
- 互斥处理口径：互斥只用于计算本实验可用流量比例。查询基础目标用户、实验场景 WAU、核心指标基线时，不要把互斥实验用户直接排除出主口径；如果为了观察污染风险另做剔除版，必须单独标注为辅助口径。

必须提醒：

```text
如果这些事件或字段不确定，可以先在埋点管理系统复核或让数据 BP 确认事件定义；你确认口径后我再走 DA 查数。
```

## 第 3 步：判断核心指标类型

样本量判断前，给已确认的核心指标分类：

| 指标类型 | 示例 | 默认处理 |
| --- | --- | --- |
| 转化率 / 比例 | 点击率、购买转化率、入口率、完成率 | 使用两比例样本量逻辑 |
| 均值 / 用户级人均值 | 人均发消息数、人均活跃天数、人均时长 | 按公司 notebook / 计算器处理；需要均值、方差或模拟输入，以及相关转化率 |
| ARPU / 收入 | ARPU、人均收入、曝光用户人均支付金额 | 按均值 / 用户级人均值处理，但标记长尾风险；需要公司 notebook / 计算器输入，不得用付费率样本量替代 |
| 次数 / 频次 | 发送次数、访问次数、查看资料次数 | 默认按均值 / 用户级人均值处理，除非数据 owner 指定计数模型 |
| 比率 | 收入 / 曝光、点击 / 展示、用户可产生多个分母的成功 / 尝试 | 要求分子、分母、聚合单元和计算器 / 数据 owner 确认；不要朴素当作简单转化率 |

如果指标类型不清楚，问：

```text
这个核心指标的分子、分母和统计单位分别是什么？比如按用户算、按曝光算，还是按订单算？
```

## 第 4 步：计算有效最小实验组比例

notebook 的 `最小实验组样本比例` 要看 WAU 是否已经扣除了灰度和互斥限制。

如果首周 WAU 是完整目标用户 + 触发场景流量，且未扣灰度/互斥：

```text
有效最小实验组比例 = 灰度比例 × 互斥后可用比例 × 最小实验组分流比例
```

示例：

```text
灰度 20%，最小实验组分流 30%，无额外互斥损耗，则有效最小实验组比例 = 20% × 30% = 6%。
```

如果 DA 查询出来的 WAU 已经是灰度后或互斥后可进入实验池的用户，则不要重复乘灰度/互斥；最小实验组比例只填组间分流中的最小实验组比例。这个判断必须基于已确认字段或 owner 明确说明，不能由 AI 推断。

输出时必须说明当前 WAU 是：

- 未扣限制的目标触发总流量。
- 已扣灰度 / 互斥后的实验池流量。
- 口径未知，待确认。

## 第 5 步：按指标类型收集输入

转化率 / 比例指标需要：

- 基线转化率。
- 最小可检测效果，或业务可接受的预期提升，可为绝对值或相对值。
- 组数。
- 组间比例。
- 计划周期。
- 如果不使用默认值，补 alpha 和 power。

脚本示例：

```bash
python3 scripts/sample_size.py --metric conversion --baseline 0.08 --relative-mde 0.1 --groups 2 --daily-traffic 50000 --duration-days 14
```

均值、ARPU、收入、次数或频次指标需要：

- 基线均值。
- 最小可检测效果，或业务可接受的预期提升，可为绝对值或相对值。
- 使用相同分析单元的历史标准差或方差。
- 过去 14 天对照组和实验组转化率或转化人数占比，用于 notebook / 模拟逻辑。
- 组数。
- 组间比例。
- 计划周期。
- 是否存在离群值，以及该指标通常如何稳定处理。

ARPU / 收入指标的观察窗口要和计划实验周期对齐。如果周期未知，先写 `实验周期内 ARPU/人均净收入`，并在问基线方差前收集计划周期。引导输出中不要默认使用 7 日或 14 日 ARPU。

当指标已有稳定用户级标准差时，可用脚本示例：

```bash
python3 scripts/sample_size.py --metric mean --baseline 3.5 --relative-mde 0.05 --stddev 8.2 --groups 2 --daily-traffic 50000 --duration-days 14
```

比率指标需要：

- 分子定义。
- 分母定义。
- 聚合单元。
- 基线比率。
- 最小可检测效果。
- 历史方差、计算器结果或数据 owner 确认。
- 组数、组间比例和计划周期。

## 第 6 步：判断灰度

当每组所需样本量已知或已由数据 owner 提供后：

- 先确定建议实验周期。商业化收入 / 转化类实验默认优先保证大约 14 天稳定观察，除非 owner 明确选择更短周期或场景有已验证短周期理由。
- 计划周期内符合条件用户 = 按实验对象和触发场景口径估算的去重用户，不是全站活跃用户。
- 每组预计有效样本 = 计划周期内符合条件用户 × 互斥后可用比例 × 正式灰度比例 × 该组分流比例。
- 判断是否足够：每组预计有效样本 >= 每组所需样本量。

反推正式灰度比例：

```text
正式灰度比例 = 每组所需样本量 / (计划周期内符合条件用户 × 互斥后可用比例 × 该组分流比例)
```

如果 A/B = 50/50、每组需要 96,887 人、计划 14 天符合条件用户约 300,000 人、互斥后可用比例为 100%：

```text
正式灰度比例 = 96,887 / (300,000 × 100% × 50%) ≈ 65%
```

如果同样条件下互斥后只剩 80% 可用流量：

```text
正式灰度比例 = 96,887 / (300,000 × 80% × 50%) ≈ 81%
```

因此，`近 7 天符合条件用户约 20 万，每组所需约 9.6 万` 时，不能因为 7 天流量看起来接近总样本就直接建议 100% 灰度，也不能建议“100% 跑几天”。应先按计划周期（通常约 14 天）估算总符合条件用户，再用互斥比例、灰度比例和组间分流比例反推。

灰度结论必须分开两类：

- 风险观察灰度：例如 10%-20% 跑 0.5-1 天，只用于检查配置、支付链路、收入、投诉、埋点是否异常，不计入正式实验周期结论。
- 正式实验灰度：按上述公式反推，保证计划周期内每组有效样本接近或超过所需样本。

互斥关系会影响最终样本量。若互斥后可用比例未知，不给最终灰度、最终实验周期、最终样本量结论或正式飞书文档；先问 owner 互斥实验占用比例或互斥后剩余可用比例。

样本量计算完成后，必须继续确认正式灰度比例，并计算每组实际可获得样本。正式灰度比例缺失时，不输出最终周期可行性、最终灰度建议或正式飞书文档。

如果总所需样本大于可获得样本，推荐一个下一步：

- 扩大实验对象或触发场景。
- 延长周期。
- 接受更大的可检测效果阈值。
- 减少实验组。
- 如果 AB 无法产出可靠结论，改用低成本验证路径。

如果瓶颈是真实场景流量，不要建议单纯提高灰度。
当 owner 已经说样本小且风险理由需要 AB 时，不要建议降低实验流量池作为“安全验证”。这时应说明实验可以继续做风险控制，但核心指标提升结论可能样本不足。

## 输出建议

面向运营时避免公式化解释。说明缺什么和下一步是什么：

```text
现在还不能判断最终灰度比例，因为核心指标是 ARPU，不是普通转化率。下一步我会先按实验场景用户口径列出具体事件、字段、分子、分母和时间窗口，确认后再查：实验周期内 ARPU 基线、用户级波动 / 公司计算器所需输入、计划周期符合条件用户，以及互斥后可用比例。
```

评审报告中说明指标类型和样本量证据是否充分：

```text
样本量与灰度：待补充。核心指标属于转化率类，但方案只给了灰度 10%，没有给场景流量、基线转化率和最小可接受提升，因此无法判断 10% 是否足够跑出结论。
```
