# 用户标签

当实验对象、推送目标人群、用户圈选、互斥、进入限制或配置准备涉及用户标签时，使用本参考。

## 结论先行

用户标签不是普通项目文档知识库。默认来源是 CMS-CLI 的推送系统 / 标签管理只读接口；本地文档、飞书索引或历史对话只能作为线索，不能替代当前 CMS 发现。

## 读取边界

- 只读发现：允许通过 `$cms` 使用 CMS-CLI 查询标签元数据、详情、层级和状态。
- 写入边界：不得新增、编辑、导入、批量开启模块、清缓存或修改任何标签；这些都属于 CMS 写操作，必须按 `$cms` 的安全规则另行确认。
- 环境边界：默认先说明查询环境。若用户没有指定生产或测试，不要把测试环境结果写成生产确认。

## 推荐发现路径

先通过 `$cms` 做 schema 发现，避免硬编码过期接口。当前已知只读入口包括：

- `cms-cli schema search 用户标签`
- `cms-cli schema search 标签管理`
- `GET /push_system/tag_meta`：分页查询用户标签元数据列表，支持按 `label_id`、`level`、`pid`、`status` 过滤。
- `GET /push_system/tag_meta/detail`：按 id 查询用户标签元数据详情。
- `GET /app/three_tag_config/list`：获取三级标签列表。

如果这些入口在当前环境不可用，停止在 `标签来源待确认`，说明缺少 CMS 权限、schema 缓存或接口变化；不要改为在项目文件里猜标签。

## 重点字段

面向 AB 实验和推送配置，优先读取并展示：

- 标签名称：用于 owner 判断业务含义。
- 备注：用于判断标签口径、圈选含义、适用场景或限制。
- 状态：只使用可用 / 启用状态的标签；停用、删除、异常或状态不明的标签不能写成可配置人群。
- 层级：一般优先使用三级标签；一级 / 二级标签只作为定位路径或父级说明。
- `label_id` / id：只作为 CMS 配置或后续交接的系统标识；不进入面向 owner、普通运营方案或飞书业务正文。

## 输出规则

面向 owner、普通运营方案或飞书业务正文时，只写中文标签名称、层级、状态和备注。例如：

```text
可用标签：长期活跃未付费用户（三级标签，状态：启用）
备注：...
```

禁止：

- 在 owner、普通运营方案或飞书业务正文中输出 `label_id`、接口字段或英文/拼音 key。
- 把状态不明或停用标签写成可用实验对象。
- 把同名标签当作同一个标签；必须看层级、备注、状态和 id。
- 因本地项目没有标签文档，就回答“没有用户标签库”。

## AB 流程中的用法

- 实验对象阶段：标签可以辅助定义“谁有资格进入实验”，但必须确认标签状态和备注是否匹配业务口径。
- 数据支持阶段：如果 owner 说“按现有标签表看”，先用标签库做术语和圈选可行性判断；不要把标签存在当成真实流量、基线或样本量已验证。
- 互斥阶段：标签可能表示策略组、活动人群或排除人群。只把它作为互斥线索；是否影响核心指标仍需按实验对象、触发场景和策略判断。
- 配置准备阶段：需要把标签名称、备注、状态、层级和系统 id 一并交给 `$cms` 做只读校验或 dry-run。
