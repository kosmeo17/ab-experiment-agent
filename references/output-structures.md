# 输出结构

用于判断如何输出评审、生成 AB 实验方案，或准备可写入飞书的结构化字段。

## 意图到输出形态

| 用户意图 | 输出形态 | 参考材料 |
| --- | --- | --- |
| 评审已有方案 | 先给结论，再给阻塞点、下一步，必要时给维度表 | `assets/review-report-template.md` |
| 引导不完整想法 | 默认只问下一个问题；不输出评审结论或长推理 | `references/question-bank.md` |
| 生成 AB 方案 | 先问下一个缺失硬门槛；运营侧字段已知后再成稿；必要时只给骨架 | `assets/ab-plan-template.md` |
| 准备或写入飞书/Lark 字段 | 输出方案字段和可选配置交接字段；只有用户明确要求时才使用飞书/Lark 文档工具 | 本文件和 `references/feishu-export.md` |

运营只需要下一步时，不要输出完整评审报告。必要性、指标、用户范围、触发场景或各组用户体验还缺失时，不要生成精美方案。不要只因为实现方式或具体配置语言未知就阻塞运营侧方案，除非它会改变实验对象、分组逻辑、触发定义或指标归因。普通运营草稿不要展示 `承载系统`、`实现方式` 或 `待产品/研发/数据讨论确认`；这些留到配置/准备度阶段。引导或方案生成中，隐藏内部判断，直接问下一个问题。

对话式引导中，除非用户要求评审报告或正式草稿，否则不要用 `已知事实 / AI 判断 / 待确认假设` 这种结构。它适合结构化文档，但对逐步引导太重。

本 skill 负责准备方案内容和评审判断。用户明确要求时，可以读写飞书/Lark 文档。除非用户在对话中提供已核验结果，否则不能声称外部数据、看板、TA 事件、Doris 指标或 DA agents 已经检查过。

## 评审输出

只在用户要求评审已有方案、检查准备度、准备飞书可用内容或输出完整报告时使用。早期想法引导不要用这个形态。

先给以下标准结论之一：

- `暂不建议进入实验设计/灰度配置`
- `不通过，必须先补齐`
- `可引导优化后调整`
- `通过`

然后输出：

- 主要原因：1 句话。
- 阻塞问题：按阶段顺序排列。
- 关键追问：默认 1 个；完整评审最多 3 个。
- 下一步：用运营能理解的语言说明。
- 维度表：只有用户要求完整评审，或方案成熟到表格能新增决策价值时才用。
- 可复用改写：只有事实足够时才给。

## AB 方案生成输出

正式飞书文档或可交付运营方案使用精简结构，避免把内部校验、自检和解释性废话写进正文：

1. 背景必要性。
2. 来源。
3. 评估指标：核心指标、过程指标、护栏指标。
4. 实验对象。
5. 实验场景。
6. 需要新增的数据支持。
7. 互斥和灰度比例：互斥、灰度比例。
8. 分组方案。
9. 样本量设置。
10. 上线前检查、实验过程中的复盘与提醒。

硬规则：任何硬门槛字段缺失时，不要编造。标记为 `待补充`，并问下一个最高优先级问题。核心指标必须是 owner 已确认口径，不能只是 AI 推荐。指标方案必须包含核心指标、过程指标和护栏指标；付费相关实验默认护栏为留存率，留存相关实验默认护栏为 ARPU/收入指标。分组方案必须通过内部 `陌生读者无疑问` 自检，否则不能进入样本量、灰度或正式飞书文档，但自检过程不要写进正式文档。实现方式不是通用草稿阻塞项；未知时不应展示在普通运营草稿里。只有实现方式会改变实验对象、分组逻辑、触发定义或指标归因时，才在成稿前追问。具体配置语言属于 `ready_to_config`，不属于普通方案草稿。

PRD 字段抽取硬规则：不要把实现范围、文案支持范围、本地化范围、示例语言、截图语言、端上支持范围或后台配置范围自动写成实验人群范围。类似 `只做中英` 只能说明文案/本地化实现限制，不能自动推出 `限定中文或英文用户`。只有来源明确写了目标用户、圈选条件、准入、排除或 owner 直接确认时，才写入用户范围；否则标为 `待确认` 并追问这是实现限制还是人群限制。

正式文档标题硬规则：不要在正式飞书文档或正式运营方案中使用 `业务域与 AI 推断` 作为章节标题。需要保留推断时，使用 `业务判断与风险说明`，或并入 `背景与必要性`，并把未确认内容写成 `待确认`。

正式草稿边界：互斥状态、样本量阶段反推的所需有效流量、最终选择的互斥可用比例与正式灰度组合，以及样本量/灰度判断还没有闭合到足以支撑当前决策前，不要把输出称为 `正式草稿` 或 `正式方案`。如果互斥关系未知，或最终互斥+灰度组合/触发流量/基线/MDE/计划周期/ARPU/均值/次数/比率类指标所需方差或计算器结果仍缺失，只能输出 `待补齐骨架` 或 `待补齐版草稿`，并明确唯一下一项缺口。互斥关系已知但互斥比例未选择时，不阻塞样本量测算；先输出所需有效流量和组合建议。存在可访问的公司 notebook、公司计算器、数据 BP 结果或用户提供的样本量文件时，未先读取/运行/引用该来源的本地公式结果不能支撑正式草稿。实现方式可以未知，但互斥和样本量/灰度不能跳过。

对话式方案生成中，不要每缺一个字段就输出完整骨架。先问下一个硬门槛问题。只有用户要求看草稿结构，或前面已有多轮信息使方案基本成型时，才输出骨架。

硬门槛字段：

- owner 想做什么。
- 问题/目标/因果依据/为什么需要 AB。
- 业务域；如果 owner 未提供，则写 `AI 推断`。
- 核心指标和必看/观察指标。
- 核心指标确认状态：owner 已确认 / AI 推荐待确认 / 待补充。
- 策略可能影响其他指标或业务线时的业务域护栏。
- 用户范围。
- 触发场景。
- 数据支持缺口。
- 组数、组间比例、各组用户体验和唯一变量差异。
- 分组自检：陌生读者是否仍会追问商品/SKU/价格计算/默认商品/促销非促销/币种四舍五入/A-B 是否相同/唯一变量。
- 互斥状态：是否要避开影响同一批用户、触发场景、价格/SKU、内容或核心指标的其他实验、活动、策略组、用户标签、Campaign 或产品规则。
- 样本量/灰度证据：按公司 notebook 口径记录首周 WAU、新 WAU 次周衰减、核心指标 14 天初始值、MDE、指标类型、有效最小实验组比例、WAU 是否已扣灰度/互斥、ARPU/均值类转化率或计算器结果；或明确 `待确认`，说明实验可为风险控制继续，但可能无法可靠判断核心指标提升。
- 上线准备。

实验成功判断和实验后动作不是逐步方案生成的硬门槛。不要把正向、负向或无变化后的动作作为必问题。起草方案时，可以提醒最终继续/停止/扩大/调整应在实验监控或复盘中，根据实际指标变化、护栏、累计样本和业务背景决定。

正式草稿交接字段：

- 实现方式/配置入口：已知时只作为内部交接或配置准备使用。未知时不要展示在普通运营草稿里；除非会影响对象、分组、触发或归因，否则不要为正式草稿强制追问。
- ABTest 系统交接字段：服务开关、组值、指标/结果回传、对照组/实验组描述。属于 `ready_to_config`。
- 推送系统交接字段：Campaign、Message、目标人群、灰度比例、AB 分组比例、`is_plan_to_send`、活动类型、触发条件、进入限制、转化事件、归因窗口、内容差异、送达/点击/转化追踪、频控和回滚/暂停动作。属于 `ready_to_config`。
- ABTest 系统和推送系统配置交接都路由给 `$cms`，从只读校验开始，任何写操作都需要明确确认。
- 正式草稿输出后，默认下一步是草稿确认：让 owner 检查目标、指标、分组和 `待确认` 标记。除非用户明确要求配置或上线准备，否则不要立即问配置负责人/路径、自测人群、上线负责人、监控负责人、回滚负责人或实现方式。

## 飞书结构化字段

准备可粘贴到飞书或通过飞书/Lark 文档工具写入的内容时，保留这些字段。只有用户明确要求文档动作且工具/授权可用时，才创建、读取或更新飞书文档。

分两层：

- 方案判断字段：解释实验为什么应该存在、如何判断结果、是否准备好。
- 配置交接字段：把用户范围、触发场景、组数、组间比例、用户体验、灰度/互斥比例、实现方式/配置入口和具体 CMS 配置字段写清楚，方便后续配置复用。只有用户要求配置或上线准备细节时才使用。

配置交接不等于实验已经配置。面向运营输出时不要承诺自动配置，只说明这些字段写清楚可以减少后续配置和评审返工。

### 基础信息

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| experiment_name | 是 | 人能读懂的标题。 |
| owner | 否 | 用户提供则保留。 |
| business_line | 否 | 用户提供则保留。 |
| business_domain | 是 | 商业化、留存/活跃、直播语聊、风控/安全、课程/学习、社交/匹配/关系、Push/召回；或在上下文推断时写 `AI 推断：...`。 |
| ai_inferred_business_assumptions | 否 | 当业务域、目标行为或风险面不是用户直接提供时，内部记录推断假设，并和已知事实分开；正式文档中不要用 `AI 推断` 做章节标题。 |
| source_links | 否 | SOP、PRD、数据文档、截图等来源。 |
| status | 否 | 使用下方状态边界。 |

状态边界：

- `idea`: 只有初始想法或策略方向。
- `reviewing`: 必要性或设计字段仍在澄清。
- `ready_to_plan_doc`: 运营侧方案已经可成为正式标准草稿或飞书文档交接。必需字段：必要性、核心指标、用户范围、触发场景、组数、组间比例、各组用户体验、数据支持状态、互斥状态，以及足够闭合的样本量/灰度证据。实现方式可以内部未知，除非会改变对象、分组、触发或归因；普通运营草稿不应展示它。如果互斥未知，或样本量/灰度仍卡在流量、基线、MDE、计划周期、ARPU/均值/次数/比率所需方差或计算器结果，方案还不能生成飞书正式文档。
- `data_feasibility_needed`: 设计已经足够定义数据问题，但基线、流量、事件/指标可用性、样本输入、监控或读数需要 `$da-agents`。
- `ready_for_launch_review`: 方案可以进入上线前评审。承载系统、追踪/看板方案、安全风险、自测范围、回滚 owner/动作和未解上线阻塞需要讨论，但具体配置可以尚未完成。
- `ready_to_config`: 方案可以稳定交给 CMS 配置。必需字段：所有 `ready_to_plan_doc` 相关字段，加上实现方式/配置入口、已知配置路径/结构或发现目标、owner/环境，以及足够安全配置的方法细节。ABTest 系统包括服务开关、组值和系统要求的指标/结果回传。推送系统包括 Campaign/Message、目标人群、灰度比例、AB 分组比例、必要时的 `is_plan_to_send`、发送规则、内容差异、转化/归因、追踪和频控。
- `ready_to_launch`: 配置完成且负责人确认通过，包括看板/追踪、双端测试是否已经通过、数据回传，以及必要时的安全监控/回滚准备。

这些状态是内部结构。面向运营输出时，要说清楚下一步，例如 `方案可以先成稿，下一步确认待补齐指标和样本量` 或 `上线前还差看板/追踪和回滚动作确认`。

不要只因为实现方式、方法特定配置值、配置负责人/路径、监控负责人、回滚动作、实验成功判断或实验后动作缺失，就阻塞 `ready_to_plan_doc`。但互斥状态或样本量/灰度判断未足够闭合时，必须阻塞飞书文档生成和正式标准草稿。如果互斥或样本量输入缺失，或流量太小，只能输出非文档待补齐骨架并说明缺口；不要创建/写入飞书文档。不要因为叙述清楚就标记为 `ready_to_config`。方法特定配置值未知时，可以说方案能在聊天里成稿，但尚未完全配置就绪。不要因为可以配置就标记为 `ready_to_launch`；上线还需要追踪/看板、自测、数据回传、监控和回滚安全。

状态表述必须和证据口径一致。若基线、流量或样本量使用的是代理事件、近似分母、历史替代窗口、未核验看板、PRD 截图或 owner 口头确认，顶部状态只能写 `基于代理口径估算`、`待正式事件复核` 或 `待上线前校验`。只有按正式实验分母/分子/事件和计算输入完成验证，才能写 `已验证`、`已定稿` 或 `可进入配置准备`。

### 互斥关系

| 字段 | 是否必需 | 说明 |

| mutual_exclusion_status | 是 | 是否需要和其他实验、活动、策略组、用户标签、Campaign、Push 策略、Paywall 规则或产品规则互斥，尤其是会影响同一批用户、触发场景、价格/SKU、内容或核心指标的规则。样本量/灰度前必须先问。 |

| overlap_risk | 否 | 同一用户进入多个策略时的污染或归因风险。 |

### 配置交接

这些字段是推荐项，不是运营侧方案必需项。只有方案必要性、指标、对象、场景和各组体验清楚后才问。

提问前先说：`下面信息主要用于后续配置同学落地实验，不影响当前继续完善实验方案。如果暂时不知道，也可以跳过。`

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| carrier_system | 否 | 内部/配置准备字段：`ABTest 系统` / `推送系统` / `后台灰度` / `待确认`。`ready_to_config` 需要，但 `ready_to_plan_doc` 不一定需要；未知时不要展示在普通运营草稿里。 |

### 样本量与灰度

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| first_week_wau | 是 | 公司 notebook 口径的实验场景首周 WAU。必须说明是否已扣灰度/互斥。 |
| new_wau_week2_attenuation | 是 | 新 WAU 次周衰减系数；可根据目标用户/场景推断，但要暴露假设。 |
| metric_baseline_14d | 是 | 核心指标过去 14 天初始值。 |
| mde_type_and_value | 是 | 相对提升或绝对提升，以及具体值。未知时，不能声称实验能检测到目标效果。 |
| required_effective_traffic | 是 | 样本量阶段反推的所需有效流量，即 `灰度比例 × 互斥后可用比例`。 |
| final_mutex_gray_combination | 是 | 最终配置组合。存在互斥时，由 owner 在组合建议中确认互斥后可用比例与正式灰度比例；没有互斥时写 `无互斥，正式灰度 <比例>`。必须确认后才能输出最终样本量/周期结论和正式文档。 |
| per_group_effective_sample | 是 | 按 `真实目标用户 × 互斥后可用比例 × 正式灰度比例 × 组间分流比例` 计算。 |
| min_experiment_group_ratio | 是 | 组间分流中的最小实验组比例。 |
| effective_min_group_ratio | 是 | 灰度、互斥和最小实验组比例合并后的有效比例；如果 WAU 已扣限制，不能重复乘。 |
| mean_or_arpu_conversion_inputs | 条件必需 | ARPU / 均值类需要过去 14 天对照组和实验组转化率或转化人数占比，以及公司 notebook / 计算器所需输入。 |
| planned_duration | 是 | 通常至少 2 周，除非有合理例外。 |
| sample_size_source | 是 | 公司 notebook / 公司计算器 / 数据 BP / 本地粗估脚本 / 手工公式 / 待确认。正式样本量必须说明来源；未实际读取或运行的文件不能写作来源。 |
| sample_size_result | 条件必需 | 公司 notebook、计算器、数据 BP 或本地脚本输出；本地脚本和手工公式只能标记为粗估 / sanity check，不能支撑正式灰度或正式周期结论。 |
| gray_or_mutex_ratio | 是 | 上线前必需，配置交接前建议确认；样本量阶段不要把它作为前置输入。 |

## 面向运营的表达

告诉 owner 下一步动作。除非用户要求完整评审，否则避免内部评审标签。

证据缺失时，说判断标准，不说具体查询步骤。除非用户要求取数方案，否则避免固定时间窗口、具体字段列表或类似 SQL 的细节。

推荐：

```text
下一步先补触发场景流量。没有这个数，就不能判断当前灰度和周期是否能跑出结论。
```

避免：

```text
你当前 Gate 6 未通过，需要补齐 sample-size evidence。
```
